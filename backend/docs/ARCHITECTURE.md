# Foundation architecture

Only config, accounts and core are implemented. Accounts owns identity, roles and
JWT lifecycle; core owns technical audit, retries, versions and operational endpoints.
Sales, masters, inventory, production, QC, recycling, dispatch, billing, costing and
external integrations remain planned. No business schema or speculative migrations exist.

## Transactional command contract

Future service entrypoints must authenticate an active actor, validate input, resolve
company/object scope from the server, and check action/object permission. Parse If-Match
with expected_version(); include aggregate identity and every version precondition in
the payload passed to execute_command(). Include all other semantic inputs in that
validated JSON payload, using decimal strings. Never hash just a subset of the command.

execute_command() opens transaction.atomic(), reruns authorize() even on replay,
creates/locks the actor+scope+action+key record, checks canonical SHA-256 payload hash,
and returns the saved result if already successful. Database uniqueness serializes
simultaneous creation of the same key. A conflicting payload returns 409. Failed
commands roll back their idempotency record as well as state and audit.

Inside operation(), lock_versioned(Model, pk, version) uses SELECT FOR UPDATE and
compares the locked version; mismatch returns 412. Apply the state change and call
advance_version(obj, update_fields=[...]). Return (safe_result_dict, http_status,
audit_kwargs). The executor inserts the audit using its actual actor and request ID,
then saves the result in the same transaction. Audit failure rolls everything back.
The original request ID remains attached to the original event; a replay gets its own
response X-Request-ID. No extra successful domain event is generated by replay.

authorize() must raise on denial, and must scope access on every invocation. Operation
must recheck transition authorization against locked state. Lock related records in
a consistent order across services to avoid deadlocks. Missing-resource scoping must
be mapped to 404 by the eventual API adapter. Only call advance_version() after a
successful lock/version check; it is a service helper, not a replacement for locks.

Only JSON-safe, authorized response data belongs in stored results; never persist tokens,
passwords, uploaded evidence or entire unfiltered request/response bodies. Audit summaries
allow before_status, after_status, changed_fields and outcome; callers must supply only
controlled safe values. Avoid personal/financial data in reason text. The runtime database
role must be restricted as documented in README. Audit records protect actor references;
deactivate accounts instead of deleting historical actors.

## Future domain use (not implemented)

- Stock services: lock exact entity/location/batch/unit balances and all QC hold sources;
  validate availability, append ledger and update projection/version in one operation.
- Approvals: lock the source, call require_independent_actor(actor, recorded_maker_id)
  where required, authorize the transition, and record the actual reviewer as audit actor.
- QC: lock subject and inspection/release state with the same lock order used by stock
  and dispatch. Releasing quality does not post inventory.
- Dispatch: lock order remainder, batch, reservation and QC holds, post OUT once and
  preserve reversal links. Do not implement these until approved workflow decisions.

Use transaction.on_commit for future notifications or a transactional outbox for durable
delivery. Never call external systems before commit. Idempotency scope must incorporate
approved company/tenant identity once known; current generic scope is not tenant isolation.
No retry-key expiry is assumed. Replay is a retained snapshot, not a fresh resource read.
No asynchronous side effects, distributed locks or stock transitions are implemented here.

## Operational boundaries

PostgreSQL is the only backend. Health is process-only; readiness checks DB access,
the user table and pending migration graph. Request IDs accept valid UUIDs or generate
a fresh UUID. Logs emit UTC JSON and omit exception bodies/SQL/request secrets.
Default permissions require authentication, while every future domain view must explicitly
use action/object authorization and filter list querysets to authorized objects. DRF
object permission hooks do not automatically scope list or create operations.
