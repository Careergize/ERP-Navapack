## API and client contract

A — Model/backend UUIDs opaque strings everywhere; keep source IDs separately. Do not parse numeric IDs, infer customers from text or reuse generated demo UUID as real receipt ID. Server assigns actor/approval fields. Decimal strings at transport and exact decimal arithmetic for validation/display; no stock posting through JS float subtraction. Lists paginated `{count,next,previous,results}`, filtered by declared server fields, deterministic ordering. Ledger responses include occurred_at/posted_at, source/lot/location/unit/partition and completeness.

A — POST create needs stable Idempotency-Key per intent. PATCH and command transitions also send last-read quoted If-Match. Semantic payload includes every precondition. Reuse key/payload after ambiguous network response; persist pending intent safely by user/account if approved, never silently issue new intent after refresh. 409 idempotency or stale-review conflict needs explicit reconciliation; 412 refreshes display without auto-resubmitting; 428 asks client to load version; 403 retains honest denial; 404 does not expose hidden objects; error envelope/request_id retained without secrets. Do not show successful stock change until committed server result. Re-fetch authoritative balances/quality after success; concurrent changes make client availability advisory.

A — Separate states: draft, submitted, awaiting approval, physically confirmed, pending recording, posted/cancelled; inspection awaiting evidence/review; held/rejected/partially released; incomplete opening. Evidence upload and scan precede command submission. Capture real measurement, timestamps, source revision, actual receiver/checker/recipient, discrepancy, approved reference and scope; no client-made approval checkbox accepted as authority.

A — Preserve token-refresh concurrency safeguards while correcting login/base path/multi-role DTO. Keep demo clearly separate and prohibit real command saves from demo identities. No mock-success fallback after server denial/unavailable persistence. Authorization on navigation is capability-based and contextual; backend remains authoritative. Reservations/conversions and costing permissions stay disabled pending separate decisions.
